# Codex 一直“正在重新连接 3/5”？先分清 429、502 和 SSE 空闲超时

Codex 已经读完仓库、开始修改文件，却突然反复显示“正在重新连接 1/5、2/5、3/5”。这个提示只表示当前请求或流式连接没有正常完成，**不能单凭它判断是 API Key、模型还是本地网络故障**。

先找到第一次失败的状态码，再分流排查：

| 现象 | 优先判断 | 第一动作 |
| --- | --- | --- |
| `429` | 请求速率、Token 速率、并发或账户额度受限 | 停止新增并发，检查额度与限流窗口 |
| `502` / `503` | 网关未获得有效上游响应 | 固定同一任务，分时段和分模型对照 |
| 固定时长后断流 | SSE 被代理、CDN 或负载均衡提前关闭 | 检查流式透传、缓冲与各层空闲超时 |
| `401` / `403` | 鉴权或模型权限 | 检查 Key、环境变量和模型授权 |
| `404` / `model not found` | 路径或模型 ID 不匹配 | 核对 `base_url`、`/v1` 和控制台模型名 |

## “3/5”不是任务进度

OpenAI 官方 Codex Advanced Configuration 展示了 Provider 级别的请求重试、SSE 重试和流空闲超时设置。例如：

```toml
[model_providers.your_gateway]
name = "Your Gateway"
base_url = "https://你的网关地址/v1"
env_key = "OPENAI_API_KEY"
wire_api = "responses"
request_max_retries = 4
stream_max_retries = 10
stream_idle_timeout_ms = 300000
```

这些参数决定短暂错误发生后客户端如何恢复，但它们不会修复错误的模型名、无权限的 Key 或不兼容的接口。把重试次数盲目调高，只会让失败更慢，还可能放大请求量和费用。

## 429：先停止“重试风暴”

429 不一定代表余额为零，还可能来自：

- 每分钟请求数或 Token 数超限；
- 多个 Agent、终端或 CI 共用同一个 Key；
- 网关对单账号或单 IP 设置并发上限；
- 多个客户端在同一时间自动重试。

建议按下面的顺序处理：

1. 暂停新的并发任务；
2. 查看服务控制台的余额、额度和限流说明；
3. 等待一个限流窗口后，只用一个小任务复测；
4. 检查是否有后台 Agent 或自动化任务共用同一 Key；
5. 确认服务恢复后，再逐步增加并发。

不要同时打开多个终端反复测试。客户端本身已经在重试时，额外的手工请求可能让限流持续更久。

## 502 / 503：做三组对照，不要先改 Key

`502` 通常表示当前网关没有从上游获得有效响应，和 `401` 的排查方向不同。可以做三组对照：

1. **同一网络、不同时间**：同一个小任务偶发成功、偶发 502，更像瞬时网关或上游故障；
2. **同一 Provider、不同模型**：只有一个模型失败时，优先检查该模型的路由与容量；
3. **同一模型、短任务与长任务**：短问答正常、真实仓库长任务中断时，重点检查 SSE 长连接与中间层超时。

每次只改变一个变量，并记录测试时间、模型、任务、状态码和 request ID。否则无法判断究竟是哪一层恢复了。

## 为什么普通聊天可用，Codex 仍会断

Codex 会持续接收流式事件，并在一个任务里多次读取文件、调用工具、执行命令和回传结果。因此，只能完成一次普通问答的“OpenAI 兼容”接口，不一定能承载 Coding Agent 的完整工作流。

至少要验证：

- Responses API 是否真实可用；
- SSE 事件能否持续、原样地传给客户端；
- 工具调用结果返回后，模型能否继续推理；
- 反向代理是否缓冲流式响应；
- CDN、Nginx 或负载均衡器是否在固定时长关闭连接；
- 错误事件、完成事件与用量记录是否完整。

如果每次都在接近 60 秒、100 秒或 5 分钟时断开，固定时长本身就是重要线索，优先检查各层超时。

## 先保留一组基线，再改重试参数

建议先使用当前配置完成基线测试，再一次只改一个参数。调高 `stream_idle_timeout_ms` 只适合已经确认服务支持 SSE、但长任务中间确实可能长时间没有事件的情况。

修改用户级 `~/.codex/config.toml` 后，完全退出并重新启动 Codex。不要把真实 API Key 写进配置截图、终端命令、Issue 或群聊。

## 15 分钟可复现验收

不要用一句问答判断“稳定”。固定同一个仓库和任务，连续测试 3 次：

1. 让 Codex 找出项目入口、测试命令和主要模块；
2. 修改两个相关文件，并运行一次测试；
3. 记录每次是否完成、重连次数、首次响应时间、总耗时和实际扣费。

只有在模型、仓库、任务和时间窗口接近时，不同 Provider 的结果才有可比性。
