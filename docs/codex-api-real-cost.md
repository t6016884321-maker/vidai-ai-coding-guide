# Codex API 价格怎么算？别只看每百万 Token，先算“每次成功任务成本”

比较 Codex API 或中转线路时，最容易误判的指标是“每百万 Token 单价”。单价低不等于真实任务成本低：如果真实仓库任务频繁断流、重试或执行失败，同一个结果可能被计费多次。

更接近开发者实际支出的指标是：

```text
每次成功任务成本 = 总计费成本 ÷ 成功完成的任务数
```

## 一套可复算的估算公式

先计算一次计费尝试的成本：

```text
单次尝试成本 =
  未缓存输入 Token ÷ 1,000,000 × 未缓存输入单价
+ 缓存输入 Token ÷ 1,000,000 × 缓存输入单价
+ 输出 Token ÷ 1,000,000 × 输出单价
```

再把失败和重试纳入：

```text
周期总成本 = 计划任务数 × 平均计费尝试次数 × 单次尝试成本
预计成功任务数 = 计划任务数 × 任务成功率
每次成功任务成本 = 周期总成本 ÷ 预计成功任务数
```

例如，同一服务的标价不变：

- 成功率从 98% 降到 70%；
- 平均计费尝试次数从 1.05 增加到 1.60；

每次成功任务的真实成本就会明显增加。这里还没有计算人工等待、重复检查 diff 和重新运行测试的时间成本。

## 输入数字从哪里来

不要凭感觉填写。固定同一个仓库、模型和任务，至少连续测 3 次，记录：

1. 未缓存输入、缓存输入和输出 Token；
2. 每个任务实际产生的计费尝试次数；
3. 是否完成了预定的代码修改和测试；
4. 控制台最终扣费；
5. 429、502、SSE 断流和工具调用失败次数。

OpenAI 官方 Codex Advanced Configuration 说明，选择启用 OTel 后，可以观察 `codex.api_request`、`codex.sse_event`、工具调用结果和每轮 Token 用量；`response.completed` 事件可包含 Token 计数。这些数据适合用来核对任务表现，但 OTel 默认关闭，启用前应评估日志目的地、隐私与安全要求。

## 为什么不能把重试次数直接当成功率

客户端重试能帮助短暂故障恢复，但不保证任务最终成功。它也不能修复错误模型名、权限不足或不兼容的 Responses API。

因此应分别记录：

- **平均计费尝试次数**：一个计划任务平均产生多少次请求或重新执行；
- **任务成功率**：最终完成验收标准的任务比例。

这两个数字一起进入成本计算，才能看出“便宜但总失败”的线路是否真的省钱。

## 比较 Provider 时保持四个条件一致

1. 同一仓库和相同代码状态；
2. 同一任务与验收标准；
3. 同一模型或可比模型；
4. 接近的测试时间窗口。

如果 A 只跑一句问答，B 跑跨文件修改和完整测试，两者成本没有可比性。
